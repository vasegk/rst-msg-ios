# Записи серверной части для iOS-клиента

Пишет серверная часть (сервер и веб, репозиторий `rst-msg`), новые записи сверху.
Свои записи и вопросы iOS-часть ведёт в [HANDOFF_ENTRY.md](HANDOFF_ENTRY.md) — так же,
как Android (`rst-msg-android/docs/HANDOFF_FROM_SERVER.md` / `HANDOFF_ENTRY.md`).

**Где протокол.** Источник правды — `PROMPT_ANDROID.md` в `rst-msg` (общий для
мобильных клиентов). Если `rst-msg` тебе не виден — снимок лежит здесь:
[server/PROMPT_ANDROID.md](server/PROMPT_ANDROID.md); опись возможностей —
[server/PARITY.md](server/PARITY.md). Снимки обновляет серверная часть при
изменениях протокола (в шапке — коммит `rst-msg`). Эталонная мобильная
реализация каждой возможности — Android-клиент (Kotlin):
`https://github.com/stepanvalitov-cyber/rst-msg-android` (на машине владельца —
`Pipiska/rst-msg android/rst-msg-android`), его `docs/HANDOFF_FROM_SERVER.md` —
подробные записи по каждой возможности с датами.

### Особенности iPhone

- **Запрет снимков экрана (6.16, одноразовые 4.16).** Android ставит
  `FLAG_SECURE`; на iOS прямого аналога нет. Принятый приём — показывать
  содержимое защищённого чата и просмотра его медиа внутри слоя
  `UITextField` с `isSecureTextEntry = true` (на снимке и записи экрана он
  пустой), плюс скрывать содержимое при `UIScreen.isCaptured`. В описании
  настройки честно: снимок с другого устройства это не остановит.
- **Push.** Без APNs iPhone не узнаёт о сообщениях при закрытом приложении:
  напоминания (3.34), упоминания в заглушённой группе (3.32), «Когда будет в
  сети» — на iOS приходят только при открытом приложении. См. ответ 1 ниже.

### Ответы на твои открытые вопросы от 2026-10-05

1. **Push на iPhone (APNs).** На сервере пока **не сделано**: поля `platform`
   в `POST /api/push/fcm/register` нет, push уходит только data-only для Android.
   Твоё предложение принято как план: `platform: "ios"` в регистрации и для
   таких токенов APNs-блок `{"aps":{"alert":{"title":"RST","body":"Новое
   сообщение"},"mutable-content":1,"sound":"default"}}` с теми же данными
   (`t`, `chat`, `id`, `to`, `m`, `r`), расшифровка — в Notification Service
   Extension. Сервер сделает это, как только у владельца появится Apple Developer
   аккаунт и APNs-ключ (.p8) будет загружен в Firebase. Клиентскую часть
   (регистрация токена с `platform`, расширение) можно готовить заранее.
2. **Universal links.** Файла `/.well-known/apple-app-site-association` на
   сервере нет — нужен TEAM_ID из того же аккаунта разработчика. Сделаем вместе
   с push. Пока — схема `rstmsg://`.
3. **Голосовые из Chrome (`audio/webm`, Opus).** Сервер не может перекодировать:
   файлы зашифрованы, он их не читает. Веб пишет в формате браузера по
   умолчанию (Chrome — WebM/Opus, Safari — MP4). Значит, уже отправленные
   голосовые и кружки в WebM iOS должен уметь проиграть сам — нужен декодер
   WebM/Opus на устройстве (Swift-обёртка над libopus + разбор WebM, или
   готовая библиотека). Перевод записи в вебе на MP4 там, где браузер умеет, —
   отдельное решение владельца; старые сообщения он не исправит.

### Совместимость, о которой легко забыть

- Шифротекст всегда начинается с `{"iv":` (ты это уже поправил — a71d567).
- Ключ из номера группы — только если настоящего нет ни у кого (уже есть).
- Своя правка собирает конверт **заново со всеми полями** исходного: `k/n/m`
  (вложение), `a`, `h`, `q`, `e`, `x`, `s` (ответ на историю) — потеря любого
  ломает сообщение у остальных.
- Пересланное не несёт `mentions`, одноразовое не пересылается, файл из
  защищённой группы сервер в другой чат не пропустит (`error`).
